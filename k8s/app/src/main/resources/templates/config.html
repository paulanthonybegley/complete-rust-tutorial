ConfigMaps, Volume Mounts & Secrets

Applications want configuration — and configuration wants to be decoupled from the image. Three ways to hand it over: as environment variables, as a mounted volume, or (never) hard-coded. This station has one real ConfigMap (web-config) and one Secret (web-secret) — pick a delivery mode and watch what lands in the pod.

1 The objects involved
ConfigMap web-config (plain)
k=v
Secret web-secret (base64)
k = v

Even though you write stringData in plaintext, the API stores data: { … } as base64. That's encoding, not encryption.

Manifest it the easy way (Secret)
apiVersion: v1
kind: Secret
metadata:
  name: web-secret
stringData:
  DB_PASSWORD: s3cr3t!

stringData is write-only sugar; read it back and it's already encoded.

2 Pick a delivery mode: env or volume env == read at boot · volume == a projected filesystem that can refresh live
3 The rotation trap update a Secret's value, and…
env var injectionvolume mount
when is the pod's copy updated? never — value baked in at pod creation soon — kubelet refreshes the projected files (with a delay)
recommended for small, static, eagerly-loaded config larger config files; live rotation; readers that re-read files
gotcha restart pods to pick up new values apps must watch the file, not cache it forever

Same lesson the video draws in chapter 12/13: the two mechanisms have different freshness contracts, and choosing between them is a real design decision.
