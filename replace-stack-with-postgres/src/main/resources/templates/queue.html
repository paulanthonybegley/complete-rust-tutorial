Job queue via FOR UPDATE SKIP LOCKED replaces Redis / RabbitMQ / Kafka

A background queue inside a plain table. Workers grab rows with FOR UPDATE SKIP LOCKED: each worker locks the row it claims, and skips rows already locked by another worker instead of waiting. No deadlocks, no dedicated broker, and ACID guarantees a message queue cannot give you — if a worker crashes mid-job, the row simply becomes claimable again.

The claim query (runs 3 workers at ~150ms polling)

WITH claimed AS (
  SELECT id FROM jobs
  WHERE status = 'pending'
  ORDER BY created_at
  LIMIT 1
  FOR UPDATE SKIP LOCKED          -- skip rows other workers already locked
)
UPDATE jobs SET status = 'running', started_at = now(), attempts = attempts + 1
FROM claimed
WHERE jobs.id = claimed.id
RETURNING jobs.id, jobs.kind;

Tip: enqueue a job with "fail": true in the payload to watch it retry up to max_attempts times before landing in the failed bucket.
